Reading the proof tree
This is an export of Lean’s actual compiled expressions, including proofs made by simp and grind. It is the proof certificate they produced, rather than a history of the tactics’ search.
▸ opens a term. In Lean mode, fun (client : DY.Participant) => … starts a proof for an arbitrary participant named client. Plain English explains the same step as “Take any client, a participant.” Split cases uses an elimination principle. Have names an intermediate term. Use applies a lemma or constructs a value.
Opening a referenced declaration shows its own body with fresh parameters. The arguments at the original application remain visible separately. Constructor and recursor leaves are kernel primitives; axioms are identified. Repeated declarations on the same path are marked to stop cycles.
The names introduced by a step and their types are shown openly. In client : DY.Participant, the colon means “client has type Participant.” A named assumption such as h_pub has a proposition as its type: that proposition is what the assumption says. There is no separate box to open for this information. Details shows all the names available at a later step and what that step must prove or produce. Lean previews omit implicit arguments that Lean infers; all of those arguments remain accessible by expanding the tree. The printed downloads use Lean’s own pretty printer.
Blue/green names jump to compiler-resolved source in the adjacent browser. For a generated helper without its own source range, the link explicitly points to its enclosing declaration. Bound variables jump to the introduction in this tree. Some kernel primitives have no source destination.
The reading trail is an explanation added for orientation. The expandable tree itself is generated from Lean. Attacker knowledge is a least fixpoint: the closure argument covers arbitrarily many attacker operations at once. Reachable traces use induction. Neither requires writing infinitely many branches.
