FRAMEWORK INTERNALS

What #combine writes for you, and how

DyLean is built from independent pieces: one file per cryptographic primitive, one per kind of trace entry, one per protocol step. A protocol assembles the pieces it needs. #combine is the command that does the assembling: given a list of pieces, it generates the sum type, the dispatching instances, and the inclusion proofs that the core of DyLean expects to find. The SignedDH example calls it eight times and gets 113 declarations back. This page explains what those declarations are and walks through the macro that produces them, from its syntax down to the two Lean issues it works around.

Every declaration mentioned here can be opened in place. Cards show the real source from ../dylean; names inside a card open the referenced declaration nested underneath.

1 · The problem it solves

In the original DY*, the type of symbolic byte strings is one fixed inductive with one constructor per primitive, the invariant on bytes is one fixed recursive function over it, and every proof about the invariant does a case split over every constructor. DyLean wants three things that this monolith cannot give. They are stated in the module documentation of DY/ALaCarte/Basic.lean:

New primitives without forkingA protocol may need a primitive DyLean did not anticipate. Users must be able to construct Bytes from the primitives they need.
Chosen security assumptionsThe invariant for a primitive encodes an assumption about it, such as whether discrete logarithms are hard. Users must be able to pick a different one.
One file per primitiveInstead of "all constructors, then all invariants, then all proofs", a file should say "here is Concat, here is its invariant, here are its proofs".

The same pressure applies to trace entries. A trace holds network messages, random values, protocol events, stored states and long-term keys, and a protocol decides which event type and which state types it uses. So the entry type is also assembled per protocol, and so is the attacker's base knowledge, the per-entry invariant, and the list of steps that count as reachable.

Data types à la carte, in one paragraph

The construction follows Swierstra's "Data types à la carte". Rather than a closed inductive, each piece is a functor: a type constructor whose parameter stands for "the recursive position". Hash contributes hash : t → Hash t, Concat contributes concat : t → t → Concat t, and so on. A family of such functors indexed by Fin n is summed by FunctorUnion, which is just a pair of an index and a value of that functor. Taking the fixpoint of the union gives the inductive type you wanted, and the fixpoint is formed by ContainerFor, which packages the union into a representation Lean's positivity checker accepts. Every piece is then a SubFunctor of the union, with an injection and a partial projection.

The other combinators have the same shape with different payloads: BytesFunctor.combine is the functor union above, ReachabilityConfig.combine makes the step input a pair of a config index and that config's input, and the combinators for lengths, invariants, attacker rules and proofs are indexed families of partial functions and partial proofs that the à-la-carte module knows how to run over a union.

Has and HasStep: how a piece finds itself in the whole

Framework code never mentions a protocol's concrete entry type. It is written against a global one, ExecTrace.Entry, and asks for an instance ExecTraceTypes.Has T whenever it wants to store or find an entry of some local type T. That instance is found by typeclass search along a chain of single steps:

Network.ExecEntryT
a piece HasStep →
generic, index 0 ExecTraceTypes.combine ExecEntryT.internal
the sum Has ↓
top-level instance: the sum is the global entry type ⇒ Has Network.ExecEntryT, by the generic instance "HasStep T U and Has U give Has T"

So, for each mechanism, the protocol has to provide: the Fin n-indexed family, the combined value, one HasStep instance per piece that names the piece by its index, the top-level instance saying the combination is the global one, and for mechanisms that carry typeclass evidence rather than data, an instance that dispatches to each piece's instance. That is between ten and thirty declarations per mechanism, all mechanical, all wrong in boring ways if written by hand. #combine writes them.

2 · What you write

SignedDH assembles itself in Examples/SignedDH/Instance.lean with six commands, plus one in the specification for the reachability config and one in the proof for the reachability theorem. Each command names one or more targets after into and the sources after from. A source is an identifier followed by arguments, so ProtocolEvent SignedDHEvent means "the protocol-event mechanism instantiated at this event type" and LongTermKeys "SignedDH PKI" names a PKI. +toplevel additionally declares the result to be the global one for this protocol.

3 · One expansion, by hand

Take the third command, #combine +toplevel into ProofEntryT from the seven entry kinds. The compiler attributes 14 declarations to it. Here is where each comes from. Generated names are highlighted; wfInst, wfInstInternal and inst are the macro's own choices and get hygienic suffixes, which is why they appear as inst._@… in the lists above.

1Split by target macro_rules for #combine

The outer command is only a loop. For every target after into it emits one #combine_one command carrying the same options, binders and sources. Here there is one target, so one command:

#combine_one +toplevel ProofEntryT from Network, Random, ProtocolEvent SignedDHEvent, …, LongTermKeys "SignedDH PKI"

2Find the rule for this target macro_rules for #combine_one … ProofEntryT

Lean picks the macro_rules whose pattern names the target identifier ProofEntryT. That rule lives next to the mechanism it serves, in DY/Trace/Invariant.lean, and calls the four helpers below in turn. Open it to follow along:

3The data combineExplicit

Two definitions. The internal one is the Fin 7-indexed family, one match arm per source in the order written, with the source's name suffixed by the target name. The second applies the mechanism's combinator to it.

@[expose] public
def ProofEntryT.internal : (id : Fin 7) → Type := fun
  | 0 => Network.ProofEntryT
  | 1 => Random.ProofEntryT
  | 2 => ProtocolEvent.ProofEntryT SignedDHEvent
  | 3 => PersistentLocalState.CompromisableState.ProofEntryT ClientInitiateState
  | 4 => PersistentLocalState.CompromisableState.ProofEntryT ClientFinishState
  | 5 => PersistentLocalState.CompromisableState.ProofEntryT ServerFinishState
  | 6 => LongTermKeys.ProofEntryT "SignedDH PKI"
  | ⟨_+7, _⟩ => False.elim (by grind)   -- see section 5: lean4#9292

@[expose, instance_reducible] public
def ProofEntryT : Type := ProofTraceTypes.combine ProofEntryT.internal

4The evidence combineTypeclass

Proof entries must erase to execution entries. Each source already has an ErasableProofEntry instance for its own pair of types, so the macro writes one instance over the index that dispatches to them with inferInstanceAs, then one instance for the combined pair, which the generic instance for combine derives from the indexed one.

public instance wfInstInternal : ∀ id, ErasableProofEntry (ExecEntryT.internal id) (ProofEntryT.internal id)
  | 0 => inferInstanceAs (ErasableProofEntry Network.ExecEntryT Network.ProofEntryT)
  | 1 => inferInstanceAs (ErasableProofEntry Random.ExecEntryT Random.ProofEntryT)
  | …
  | ⟨_+7, _⟩ => False.elim (by grind)

public instance wfInst : ErasableProofEntry ExecEntryT ProofEntryT :=
  inferInstanceAs (ErasableProofEntry (ExecTraceTypes.combine ExecEntryT.internal) (ProofTraceTypes.combine ProofEntryT.internal))

The last line is the whole trick of the typeclass helpers. ExecEntryT is definitionally the combination, so stating the instance at the combination and coercing it with inferInstanceAs lets the generic instance for combine fire.

5The inclusions mkHasStep

One instance per source. Each says the source's entry type steps into the combined one, and proves it by pointing at the generic instance for combine at the right index.

public instance inst : ProofTraceTypes.HasStep Network.ProofEntryT ProofEntryT :=
  inferInstanceAs (ProofTraceTypes.HasStep (ProofEntryT.internal 0) (ProofTraceTypes.combine ProofEntryT.internal))
public instance inst : ProofTraceTypes.HasStep Random.ProofEntryT ProofEntryT :=
  inferInstanceAs (ProofTraceTypes.HasStep (ProofEntryT.internal 1) (ProofTraceTypes.combine ProofEntryT.internal))
-- … five more, indices 2 to 6

6Make it global +toplevel, rule-specific

Only with +toplevel. The rule declares the combination to be the protocol's proof-entry type and gives it the trivial Has instance, so the chain in section 1 closes:

public instance : ProofTraceTypes where ProofT := ProofEntryT      -- named instProofTraceTypes_examples by Lean
public instance : ProofTraceTypes.Has ProofEntryT := inferInstanceAs (ProofTraceTypes.Has ProofTrace.Entry)

7The bridge mkHasCombine

Also only with +toplevel. It restates the Has instance at the unfolded combination, from the one at the name. Section 5 explains why Lean needs this nudge.

public instance inst [ProofTraceTypes.Has ProofEntryT] : ProofTraceTypes.Has (ProofTraceTypes.combine ProofEntryT.internal) :=
  inferInstanceAs (ProofTraceTypes.Has ProofEntryT)
Count. 2 definitions + 2 erasability instances + 7 step instances + 2 top-level instances + 1 bridge = 14, which is what the compiler reports for that span above. The eight anonymous inst names are the seven steps and the bridge.

4 · The implementation

The macro is 323 lines in DY/Meta/CombineMacro.lean, plus one macro_rules block per mechanism in the file that defines the mechanism. It is an ordinary Lean macro, so everything happens by rewriting syntax to syntax in MacroM; nothing elaborates or inspects types. That is why it is simple, and also why its error messages arrive late, from the elaborator, when a generated declaration fails to typecheck.

#combine +toplevel into A, B from s₁ … sₙuser command →loop #combine_one +toplevel A from s₁ … sₙand the same for B →macro_rules by target the A rulein the file that defines A →calls

→ mkNullNode [cmd, cmd, …]declarations, elaborated normally

Syntax

Three syntax categories and two commands. A source is an identifier with trailing arguments, so arguments reach the generated code untouched. A target is an identifier with optional binders of its own. Trailing commas are allowed, which is why every invocation in SignedDH ends with one.

declare_syntax_cat combine_from
syntax ident term:arg* : combine_from                       -- e.g. ProtocolEvent SignedDHEvent

declare_syntax_cat combine_into
syntax ident bracketedBinder* : combine_into                -- e.g. ProofEntryT, or SubF (n : Nat)

declare_syntax_cat combine_option
syntax "+toplevel " : combine_option

syntax "#combine_one " combine_option* combine_into " from " combine_from,*,? : command
syntax "#combine " combine_option* bracketedBinder* " into " combine_into,*,? " from " combine_from,*,? : command

Dispatch to #combine_one

The only rule defined for #combine itself concatenates the command's binders with each target's own binders and emits one #combine_one per target. Returning a mkNullNode of commands is how a Lean macro expands to several commands at once.

macro_rules
  | `(command| #combine $options:combine_option* $globalParams:bracketedBinder* into $targets,* from $sources,*) => do
    let mut cmds := #[]
    for target in targets.getElems do
      let `(combine_into| $id:ident $localParams*) := target | panic! "??"
      let params := globalParams ++ localParams
      cmds := cmds.push (← `(command| #combine_one $options* $id:ident $params* from $sources,*))
    return mkNullNode cmds

There is no table of targets. #combine_one is dispatched by Lean's own macro mechanism: each mechanism adds a macro_rules whose pattern has its name in the target position, and Lean tries the rules until one matches. Adding a mechanism therefore means adding a rule, not editing the macro.

The four helpers

Each helper takes the binders, the sources and a small config of syntax builders, and returns an array of commands. The makeSimple constructors cover the common case where the config can be derived from a handful of names. Open each to see the quotations that produce the code in section 3.

Two details worth noticing in the source. Names are built with modifyBase (· ++ config.name), so the source identifier Network becomes Network.ProofEntryT while keeping the source's position for error reporting through mkIdentFrom. And the generated instance names are created with withFreshMacroScope, which is what makes them hygienic: two expansions in the same namespace cannot collide, at the price of unreadable names.

Two things the table hides. Without +toplevel, most rules prepend instance binders such as [ExecTraceTypes] [ProofTraceTypes] to every generated declaration, so the combination can be stated inside a section that is still parametric in the global types; with +toplevel those binders are dropped because the command itself is defining the global types. And the SubBaseAttackerKnowledgeTheorem family shows the escape hatch: a rule may simply emit another #combine_one with adjusted binders, which Lean expands again.

5 · Two Lean issues the macro works around

Exhaustive matches on Fin n

Every indexed family is written as a match with one literal arm per index. Lean's exhaustiveness check for literal patterns on Fin n gives up above a certain size. The macro appends an unreachable catch-all arm whose body is a proof by grind that no such index exists, and comments the line with the issue number.

-- workaround for https://github.com/leanprover/lean4/issues/9292
arms := arms.push (← `(Parser.Term.matchAltExpr| | ⟨ _+$(quote sources.size), _ ⟩ => False.elim (by grind)))

lean4#9292, "Pattern matching on Fin n breaks exhaustivity for n > 15", still open at the time of this snapshot.

Top-level instances unfold differently

mkHasCombine exists only because typeclass resolution treats a top-level instance differently from a local one when the goal mentions the unfolded combination rather than its name. The macro restates Has X at Has (X.combine X.internal), and only when +toplevel is set, since local instances do not show the problem. The doc comment on the helper says plainly that relying on the local behaviour is an unintended feature of Lean that might change.

lean4#13571, "Inconsistent behavior in typeclass resolution (local vs top-level instance)", open.

Consequence for readers. When you see an instance named inst._@.Examples.SignedDH.Instance… in a proof tree or a search, it is one of these generated inclusions, not something a person wrote. The toolkit page labels them "hygienic instance".

6 · Adding a mechanism

The module documentation gives the recipe, and every existing rule follows it:

  1. Define the mechanism around a combinator X.combine : (Fin n → X) → X, with a generic X.HasStep (xs id) (X.combine xs) instance and a generic "HasStep and Has give Has" instance, as ExecTraceTypes does in section 1.
  2. Give each piece a declaration named <piece>.X, since the macro forms source names by appending the target name.
  3. Add macro_rules | `(command| #combine_one $options* X $params* from $sources,*) => … in the same file, call combineExplicit or combineTypeclass for the value, mkHasStep for the inclusions, and append the top-level instances behind parseOptions options |>.toplevel.
  4. If the mechanism is data that other declarations unfold, add mkHasCombine for the top-level case.

Nothing registers the new rule anywhere. Importing the file is enough, which is the point: a user's own primitive, in a user's own file, participates in #combine on equal terms with Hash.
